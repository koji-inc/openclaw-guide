    第10章：セキュリティとペアリング¶

    「家の鍵をかけずに寝る人はいない。でも、AIエージェントに鍵をかけ忘れている人は多い。OpenClawのセキュリティは『完全に安全な設定は存在しない』という正直な前提から始まる。目標は完璧ではなく、意図的であることだ。」

    前章でエージェントに自律性を与えた。Heartbeatで30分おきに巡回させ、Cronで定時タスクを仕込み、Webhookで外部イベントに即応する——24時間365日、あなたの代わりに動くエージェントが完成した。しかし、自律的に動くということは「暴走したらどうする？」「権限を越えたら？」という問いが避けて通れないということでもある。

    家に例えるなら、鍵（認証）をかけ、誰を入れるか（ペアリング）を決め、部屋を仕切り（サンドボックス）、金庫に大事なものをしまい（シークレット）、防犯カメラ（監査）を設置する——この章では、OpenClawの安全装置の全体像を解き明かす。キーワードは爆発半径（blast radius）の制御。何かが起きても、被害を最小限に閉じ込める設計だ。

    この章を読み終える頃にわかること¶

    • OpenClawのセキュリティ設計思想（シングルユーザー信頼モデル）と5つの信頼境界
    • DMペアリングとノードペアリングの仕組みと設定方法
    • Gateway認証の4つのモードと使い分け
    • サンドボックスの種類・モード・スコープの選び方
    • シークレット管理（SecretRef）の仕組みと安全な運用方法
    • openclaw security audit で自分の設定を診断する方法
    • 脅威モデルATLASの読み方と、Critical脅威への対策

    10.1 セキュリティモデルの全体像 — 「意図的であること」¶

    個別の設定を触る前に「OpenClawがどんな考え方でセキュリティを設計しているか」を知っておこう。地図を見てから街を歩くのと同じだ。全体像が見えていれば、以降の各セクションが腹落ちしやすくなる。

    10.1.1 シングルユーザー信頼モデル¶

    OpenClawのセキュリティモデルは「パーソナルアシスタント信頼モデル」と呼ばれる。1つのGatewayにつき1つの信頼されたオペレーター境界——つまりシングルユーザー前提で設計されている。

    これは重要なポイントだ。OpenClawは複数の敵対的なユーザーが1つのGateway/エージェントを共有する「敵対的マルチテナント」を想定していない。もし複数の信頼できないユーザーを隔離する必要があるなら、信頼境界ごとにGatewayを分離する（別OSユーザーや別ホストで運用する）のが推奨される。

    10.1.2 3つの設計原則 — アクセス制御 > インテリジェンス¶

    OpenClawのセキュリティは3つの原則に基づいて階層的に設計されている。

    1. Identity first（まず身元確認） — DMペアリングや許可リストで「誰がボットと話せるか」を決定する。これが最外殻の防御だ
    2. Scope next（次にスコープ） — グループ許可リスト、メンション要件、ツールポリシー、サンドボックス、デバイス権限で「何ができるか」を制限する
    3. Model last（モデルは最後） — LLMモデルは操作可能だと仮定する。仮に操作されても、爆発半径（blast radius）が限定されるように設計する

    この順番が重要だ。モデルの「賢さ」に頼ってセキュリティを担保しようとするのではなく、アクセス制御という構造的な防御を先に敷いている。モデルがどんなに騙されても、そもそもアクセスできない領域には手が届かない——これがOpenClawの哲学だ。

    10.1.3 5つの信頼境界（Trust Boundary Matrix）¶

    OpenClawのセキュリティは5層の信頼境界で構成されている。

    信頼境界 役割 主な仕組み
    TB1: チャネルアクセス 誰がエージェントと話せるか Device Pairing（30秒猶予期間）、AllowFrom/AllowList、Token/Password/Tailscale認証
    TB2: セッション隔離 会話はどう分離されるか セッションキー（agent:channel:peer）、エージェントごとツールポリシー、トランスクリプトログ
    TB3: ツール実行 コードはどこで動くか Docker sandbox / Host（exec-approvals）、Node リモート実行、SSRF保護（DNSピニング+IPブロック）
    TB4: 外部コンテンツ 外部データはどう扱うか 外部コンテンツのXMLタグラッピング、セキュリティ注意書き挿入
    TB5: サプライチェーン スキルは安全か ClawHub スキル公開（semver、SKILL.md必須）、パターンベースモデレーション、VirusTotalスキャン（開発中）

    TB1からTB5に向かって、外側から内側へ順番に防御が深くなっていく。この章ではTB1〜TB3を中心に、具体的な設定方法を見ていく。

    💬 こうじの実感： 「完全に安全なセットアップは存在しない」って最初ドキッとしたけど、考えてみれば当たり前だよね。スマホだってパスワードかけてても盗まれたらアウトなわけで。大事なのは「自分が何を守ってて、何を許容してるか」を把握してること。OpenClawはそこを正直に言ってくれるのが好き。

    ⚠️ ここに注意: OpenClawは「1人のオーナーが1つのGatewayを使う」前提で設計されている。複数の信頼できないユーザーが同じGatewayを共有する構成は推奨されない。必要なら信頼境界ごとにGatewayを分離すること。

    10.2 ペアリング — 「誰と話すか」を決める¶

    セキュリティの第一歩は「誰がエージェントに話しかけられるか」の制御だ。ペアリングはOpenClawを使い始めて最初に触るセキュリティ機能であり、日常的に最も意識する部分でもある。

    10.2.1 DMペアリング — チャネルレベルの門番¶

    DMペアリングは「知らない人からのメッセージをどう扱うか」を制御する仕組みだ。WhatsApp、Discord、Telegram——どのチャネルでも共通のポリシーが使える。

    DMポリシーの4段階¶

    dmPolicy（または *.dm.policy）で設定できるポリシーは4つある。

    ポリシー 動作 ユースケース
    pairing（デフォルト） 不明な送信者にペアリングコードを送信し、承認されるまで無視 個人利用（推奨）
    allowlist 不明な送信者をブロック（ペアリング自体なし） 完全に閉じた運用
    open 誰でもDM可能（"*" の明示的オプトイン必須） 公開ボット
    disabled 受信DMを完全無視 DM不要な場合

    デフォルトの pairing が最もバランスが良い。初めての送信者にはペアリングコードが送られ、あなた（オーナー）がCLIで承認するまで、その人のメッセージは処理されない。

    ペアリングの具体的な流れ¶

    1. 未知のユーザーがエージェントにDMを送る
    2. エージェントがペアリングコードを生成し、ユーザーに通知する
    3. コードの有効期限は1時間。繰り返しDMが来ても、新規リクエストが作成されるまでは再送信しない
    4. オーナーがCLIで承認する：
    # 保留中のペアリングリクエストを確認
openclaw pairing list <channel>

# コードを指定して承認
openclaw pairing approve <channel> <code>
    1. 承認されたペアは ~/.openclaw/credentials/<channel>-allowFrom.json に保存される
    2. 非デフォルトアカウントの場合: <channel>-<accountId>-allowFrom.json

    保留リクエストにはチャネルあたり3件の上限がある。スパム的なペアリング要求が溜まるのを防ぐ仕組みだ。

    💬 こうじの実感： 最初WhatsAppでDMしたら「ペアリングコードを送りました」って言われて「は？」ってなった。でも考えたら、知らない人からのDMをいきなり処理されたら怖いよね。この仕組みがあるおかげで「こいつは晃一さんだな」って確認してから話し始められる。

    ⚠️ ここに注意: open ポリシーは便利だが、誰でもエージェントと会話できてしまう。公開ボットを意図的に作る場合以外は使わないこと。設定するには "*" の明示的なオプトインが必須だ。

    10.2.2 ノードペアリング — デバイス接続の認証¶

    DMペアリングが「メッセージを送る人」の認証なら、ノードペアリングは「接続するデバイス」の認証だ。macOSアプリやiPadからGatewayに接続する際、そのデバイスが信頼できるかを確認する仕組みである。

    ノードペアリングの仕組み¶

    Gatewayが「どのノードが参加可能か」のソース・オブ・トゥルース（信頼の源泉）となる。UI（macOSアプリ等）は承認/拒否のフロントエンドにすぎない。

    フローを見てみよう：

    1. ノードがGatewayのWebSocketに接続し、ペアリングリクエストを送信する
    2. Gatewayが保留リクエストを保存し、node.pair.requested イベントを発行する
    3. オーナーがCLI（またはUI）で承認 or 拒否する
    4. 承認時、Gatewayが新しいトークンを発行する（再ペアリング時はトークンローテーション）
    5. ノードがそのトークンで再接続し、ペアリングが完了する

    重要な点がいくつかある：

    • 保留リクエストの有効期限は5分（DMの1時間よりかなり短い）
    • node.pair.request メソッドは冪等（何度呼んでも同じ結果）
    • 承認は常に新トークンを生成する。node.pair.request からトークンが返ることはない

    承認済みノードは ~/.openclaw/nodes/paired.json に、保留リクエストは pending.json に保存される。

    CLI操作¶

    # 保留中のペアリングリクエストを確認
openclaw nodes pending

# 承認
openclaw nodes approve <requestId>

# 拒否
openclaw nodes reject <requestId>

# 接続中ノードの状態確認
openclaw nodes status

# ノードに名前をつける
openclaw nodes rename --node <id|name|ip> --name "Living Room iPad"

    Auto-approval（macOS）¶

    macOSアプリには silent: true マークとSSH接続検証による自動承認の仕組みがある。ローカルのmacOSアプリがSSHで接続を検証できる場合、ペアリング承認を自動的にスキップできる。

    なお、Gateway認証レベルでも別の自動承認がある（10.3節で後述）。ローカル接続（ループバックまたはGateway自身のTailscaleアドレス）からのデバイスペアリングは自動承認されるが、他のTailscaleピアからのリクエストはペアリング承認が必要だ。この2つは異なるレイヤーの話なので混同しないよう注意。

    💡 コラム：なぜノードペアリングは5分でDMは1時間？ ノードペアリングはデバイスが物理的に近くにある状態で行う操作なので、短い猶予で十分だ。一方DMペアリングは、別端末でCLI承認する必要があり、すぐに対応できないこともあるため長めに設定されている。また、ノードペアリングはトークン発行を伴うため、保留状態が長いとセキュリティリスクが高まる。ユースケースに合わせた現実的なタイムアウト設計だ。

    10.3 Gateway認証 — 接続を守る¶

    ペアリングで「誰と話すか」を決めた。次はGateway自体への接続をどう守るかだ。外部からの不正アクセスを防ぐ最も基本的な防御線であり、ここが突破されれば内側のセキュリティは全て無意味になる。

    10.3.1 4つの認証モード¶

    Gateway認証（gateway.auth.mode）には4つのモードがある。

    モード 仕組み 推奨度
    token 共有ベアラートークン ⭐ 推奨
    password パスワード認証（env: OPENCLAW_GATEWAY_PASSWORD 推奨） ○ 手軽
    trusted-proxy ID認識リバースプロキシに認証を委任 △ 上級者向け
    none 認証なし ❌ 非推奨（critical警告）

    最も重要なポイント: 認証が未設定の場合、GatewayはWebSocket接続を拒否する（fail-closed）。「認証を設定し忘れたらフルオープン」ではなく「設定し忘れたら誰も接続できない」という安全側に倒した設計だ。

    トークンの生成は簡単だ：

    openclaw doctor --generate-gateway-token

    これだけで十分にランダムなトークンが生成される。

    ⚠️ ここに注意: auth.mode: "none" は絶対に本番で使わないこと。Gatewayが外部に露出している場合、誰でもエージェントを操作できてしまう。OpenClawは認証未設定時にcritical警告を出すが、それを無視してはいけない。

    💬 こうじの実感： 正直、最初は token 一択でいい。Trusted Proxyとか聞くと「うっ」ってなるけど、それは企業向けの話。個人利用なら token + Tailscaleで十分すぎるくらい守れるよ。

    10.3.2 Trusted Proxy Auth（上級）¶

    企業や複数ユーザー環境では、Pomerium、Caddy + OAuth、nginx + oauth2-proxy、Traefik + Forward Auth といったID認識リバースプロキシの背後でOpenClawを運用したい場合がある。Trusted Proxy Authはそのための仕組みだ。

    仕組み¶

    1. リバースプロキシがユーザーを認証する（OAuth/OIDC/SAML等）
    2. プロキシが認証済みユーザーIDをヘッダーで付与する（例: x-forwarded-user）
    3. OpenClawが gateway.trustedProxies でプロキシのIPを確認する
    4. ヘッダーからユーザーIDを抽出し、検証OKならリクエストを承認する

    設定例はこうなる：

    {
  gateway: {
    trustedProxies: ["10.0.0.1"],
    auth: {
      mode: "trusted-proxy",
      trustedProxy: {
        userHeader: "x-forwarded-user",         // 必須
        requiredHeaders: ["x-forwarded-proto"],  // オプション
        allowUsers: ["nick@example.com"],        // オプション（空=全認証ユーザー許可）
      },
    },
  },
}

    allowUsers を空にすると、プロキシが認証した全ユーザーがアクセスできる。特定のユーザーに絞りたい場合はメールアドレス等を列挙する。

    Trusted Proxy Authが有効な場合、Control UIのWebSocketセッションはデバイスペアリング不要で接続できるようになる。プロキシが認証を代行しているためだ。

    対応プロキシと対応ヘッダーの例： - Pomerium: x-pomerium-claim-email - Caddy + OAuth: カスタムヘッダー - nginx + oauth2-proxy: x-forwarded-user - Traefik + Forward Auth: カスタムヘッダー

    10.3.3 Tailscale Serve認証¶

    Tailscaleを使ってGatewayを公開している場合、Tailscale Serve経由の認証も利用できる。

    {
  gateway: {
    auth: {
      allowTailscale: true  // Serveのデフォルト
    }
  }
}

    allowTailscale: true にすると、Tailscale Serveが付与するヘッダー（tailscale-user-login）を認証に使う。x-forwarded-for ヘッダーはローカルのTailscaleデーモン（tailscale whois）で検証される。

    ただし注意点がある。HTTP APIエンドポイント（/v1/*, /tools/invoke 等）はTailscale認証だけでは不十分で、別途token/password認証が必要だ。Tailscale認証はあくまでWebSocket接続（チャット）のレイヤーでの認証であり、APIアクセスには従来の認証が引き続き求められる。

    10.4 サンドボックス — ツール実行の隔離¶

    認証で「誰が入るか」を制御した。次は「入った後に何ができるか」の制限だ。サンドボックスはエージェントのツール実行をホストから隔離する重要な防御レイヤーであり、第8章で紹介したツールの「実行環境」を制御する。

    10.4.1 サンドボックスの種類¶

    サンドボックスには3つのバックエンド（agents.defaults.sandbox.backend）がある。

    バックエンド 実行場所 セットアップ ワークスペース ブラウザサンドボックス
    docker（デフォルト） ローカルコンテナ scripts/sandbox-setup.sh バインドマウント or コピー 対応
    ssh SSH接続可能なホスト SSHキー + ターゲットホスト リモート正規（シード1回） 非対応
    openshell OpenShell管理サンドボックス OpenShellプラグイン有効化 mirror or remote 未対応

    ほとんどのケースでは docker を使えばいい。SSHバックエンドは「強力なリモートマシンでコードを実行したい」場合、OpenShellは「マネージドなサンドボックス環境を使いたい」場合の選択肢だ。

    10.4.2 モードとスコープ¶

    サンドボックスの動作を制御する3つの軸がある：モード（いつサンドボックスを使うか）、スコープ（コンテナの共有範囲）、ワークスペースアクセス（ファイルアクセスの権限）だ。

    モード（sandbox.mode）¶

    モード 動作
    "off" サンドボックスなし。全てホストで実行
    "non-main" 非メインセッション（グループチャット、チャネル等）のみサンドボックス化
    "all" 全セッションをサンドボックス化

    推奨は "non-main" から始めることだ。メインセッション（あなたとの1対1のDM）はホストで実行し、グループチャットのように他人のメッセージに反応する可能性がある場面ではサンドボックスに閉じ込める。慣れてきたら "all" に移行するのが良い。

    スコープ（sandbox.scope）¶

    スコープ 動作
    "session"（デフォルト） セッションごとに1コンテナ
    "agent" エージェントごとに1コンテナ
    "shared" 全サンドボックスセッションで1コンテナ共有

    "session" がデフォルトで最も安全だ。セッションが終わればコンテナも消える。"shared" は複数セッション間でファイルを共有したい場合に使うが、隔離レベルは下がる。

    ワークスペースアクセス（sandbox.workspaceAccess）¶

    設定 動作
    "none"（デフォルト） ~/.openclaw/sandboxes のサンドボックス専用ワークスペースのみ
    "ro" エージェントワークスペースを /agent に読み取り専用マウント
    "rw" エージェントワークスペースを /workspace に読み書きマウント

    💬 こうじの実感： サンドボックスの設定は「保険」みたいなもの。普段は何も起きないけど、万が一エージェントが変なコマンドを実行しても、コンテナの中で閉じ込められる。特にグループチャットで他人のメッセージに反応する場合は必須だと思う。

    10.4.3 Dockerサンドボックスの詳細¶

    デフォルトバックエンドであるDockerサンドボックスについて、もう少し詳しく見ておこう。

    イメージ¶

    イメージ 用途 セットアップ
    openclaw-sandbox:bookworm-slim デフォルト scripts/sandbox-setup.sh
    openclaw-sandbox-common:bookworm-slim 共通ツール版 scripts/sandbox-common-setup.sh
    ブラウザ版 ブラウザ操作が必要な場合 scripts/sandbox-browser-setup.sh

    ネットワーク制限¶

    Dockerサンドボックスはデフォルトでネットワークなしだ。コンテナ内からインターネットにアクセスすることはできない。これは意図的な設計で、エージェントが外部にデータを送信するリスクを根本から断つ。

    さらに以下の制限がある： - network: "host" はブロックされる - network: "container:<id>" はデフォルトでブロックされる（dangerouslyAllowContainerNamespaceJoin: true で解除可能だが非推奨）

    セキュリティデフォルト¶

    • 危険なバインドソース（docker.sock, /etc, /proc, /sys, /dev）は自動的にブロックされる
    • readOnlyRoot: true でルートファイルシステムを読み取り専用にできる

    何がサンドボックス化されているか分からなくなったら、以下のコマンドでデバッグできる：

    openclaw sandbox explain

    ⚠️ ここに注意: sandbox.mode: "off" + exec.security: "full" の組み合わせは最も危険な設定だ。エージェントがホスト上で任意のコマンドを承認なしに実行できてしまう。この2つを同時に設定するのは避けること。

    10.5 シークレット管理 — 秘密を安全に扱う¶

    サンドボックスで実行環境を隔離した。次は、APIキーやトークンといった「秘密の情報」をどう管理するかだ。漏洩すれば全てが台無しになる、最も慎重に扱うべき領域である。

    10.5.1 モデル認証の管理¶

    エージェントがLLMを呼び出すには、モデルプロバイダーへの認証が必要だ。OpenClawには2つの認証方式がある。

    APIキー方式（推奨）¶

    特に長時間稼働するGateway（デーモン運用）ではAPIキー方式が推奨される。環境変数で設定するのが基本だ：

    # 環境変数に設定
export ANTHROPIC_API_KEY="sk-ant-..."
export OPENAI_API_KEY="sk-..."

# デーモン用は ~/.openclaw/.env に設定
echo 'ANTHROPIC_API_KEY=sk-ant-...' >> ~/.openclaw/.env

    APIキーの優先順序は以下の通り： 1. OPENCLAW_LIVE_<PROVIDER>_KEY — 最優先 2. <PROVIDER>_API_KEYS — 複数キー（カンマ区切り） 3. <PROVIDER>_API_KEY — 標準 4. <PROVIDER>_API_KEY_* — ワイルドカード

    レートリミットエラー（429等）が発生した場合のみ次のキーでリトライする。重複キーは自動的に除外される。

    setup-token方式¶

    Claude CLIで claude setup-token を実行してトークンを取得し、openclaw models auth setup-token --provider anthropic でOpenClawに登録することで、サブスクリプション認証を使うこともできるが、Anthropicがサブスクリプション利用をブロックする場合があるため、APIキー方式の方が安定する。

    認証の状態は以下のコマンドで確認できる：

    openclaw models status           # 現在のモデル認証状態
openclaw models status --check   # exit 1=期限切れ/不在, exit 2=期限間近
openclaw doctor                  # 全体的な健康チェック

    10.5.2 SecretRefコントラクト¶

    APIキー以外にも、チャネルのトークン、外部サービスの認証情報など、さまざまなシークレットを管理する必要がある。OpenClawはこれらをSecretRefという統一的な仕組みで扱う。

    統一形式¶

    { source: "env" | "file" | "exec", provider: "default", id: "..." }

    3つのソースから秘密の値を取得できる：

    1. env（環境変数） — 最もシンプル。IDは ^[A-Z][A-Z0-9_]{0,127}$ のパターンに従う。

    { source: "env", id: "DISCORD_BOT_TOKEN" }

    2. file（JSONファイル） — JSONファイルの特定のキーを参照する。IDはRFC6901 JSON Pointerだ。 - mode: "json": JSONオブジェクトのポインタ解決 - mode: "singleValue": ファイル全体を値として返す

    3. exec（外部コマンド） — 1Password CLI、HashiCorp Vault、sopsなどの外部シークレットマネージャーと連携する。コマンドは絶対パスで指定し、シェルは経由しない。

    # 1Password CLI
op read "op://vault/item/field"

# HashiCorp Vault
vault kv get -field=api_key secret/openclaw

# sops
sops -d --extract '["api_key"]' secrets.enc.yaml

    ランタイムモデル¶

    SecretRefの解決には重要な特性がある：

    • 即時解決（eager）: アクティベーション時に解決し、リクエストパスでは遅延しない
    • 起動時fail-fast: アクティブなSecretRefが解決できなければ起動を中止する
    • リロード時atomic swap: 全て成功するか、前回の正常なスナップショットを維持するか。中途半端な状態にはならない
    • アクティブサーフェスフィルタリング: 無効なサーフェス（例: 無効化されたチャネル）の未解決refはブロックしない

    💬 こうじの実感： シークレット管理って聞くと「面倒くさそう…」って思うけど、最初は環境変数に入れるだけでOK。1PasswordやVault連携は「APIキーが10個超えたな」ってなってから考えれば十分。

    10.5.3 シークレット運用¶

    日々のシークレット運用にはCLIコマンドが用意されている：

    openclaw secrets audit --check       # 監査（平文値、未解決ref、シャドウイング等をチェック）
openclaw secrets configure           # インタラクティブな設定ウィザード
openclaw secrets apply --from <plan> # プランファイルから一括適用
openclaw secrets reload              # ランタイムリロード（atomic swap）

    secrets audit は以下をチェックする： - 設定ファイルに残っている平文の秘密値 - 未解決のSecretRef（存在しない環境変数やファイルの参照） - 優先度シャドウイング（同じキーが複数箇所で定義されている） - レガシー残留物（古い形式のシークレット設定）

    一方向安全ポリシー¶

    OpenClawはシークレットの平文バックアップを一切書かない。これは意図的な設計だ。プリフライトチェック → ランタイム検証 → コミットという一方向のフローで、「万が一バックアップが漏れたら全キーが流出」というリスクを根本から排除している。

    ファイルパーミッション推奨¶

    パス 推奨パーミッション
    ~/.openclaw/ 700
    ~/.openclaw/openclaw.json 600

    クレデンシャルストレージマップ¶

    どの認証情報がどこに保存されるかを把握しておくことも重要だ：

    資格情報 保存場所
    WhatsApp ~/.openclaw/credentials/whatsapp/<accountId>/creds.json
    Telegram bot token config/env or channels.telegram.tokenFile
    Discord bot token config/env or SecretRef
    Slack tokens config/env
    ペアリング許可リスト ~/.openclaw/credentials/<channel>-allowFrom.json
    モデル認証プロファイル ~/.openclaw/agents/<agentId>/agent/auth-profiles.json
    ノードペアリング ~/.openclaw/nodes/paired.json, pending.json

    💡 コラム：なぜ「一方向安全ポリシー」なのか？ OpenClawはシークレットの平文バックアップを一切書かない。「万が一バックアップが漏れたら全キーが流出」というリスクを根本から排除するためだ。不便に感じるかもしれないが、セキュリティは利便性とのトレードオフ。OpenClawは「安全側に倒す」を選んでいる。シークレットマネージャー（1Password等）を使えば、OpenClaw側にバックアップがなくても困ることはない。

    10.6 ツールポリシーとelevated権限 — 行動範囲の制限¶

    サンドボックスが「どこで実行するか」なら、ツールポリシーは「何を実行できるか」だ。第8章で詳しく扱った内容なので、ここではセキュリティの文脈で重要なポイントに絞って見ていく。

    10.6.1 ツールポリシーのセキュリティ視点¶

    ツールポリシーは2つのレイヤーで構成されている（詳細は第8章参照）：

    1. ツールプロファイル (tools.profile) — ベースの許可リスト
    2. グローバル/エージェント別ポリシー (tools.allow / tools.deny) — 追加の許可・拒否

    セキュリティ上最も重要なルールは「deny は常に最優先」ということだ。allow に入っていても deny に入っていればブロックされる。これはハードストップであり、/exec コマンドでもオーバーライドできない。

    sandbox vs tool-policy vs elevated の使い分け¶

    この3つの違いが分かりにくいので、整理しておこう：

    コントロール 何を決めるか 対象
    Sandbox ツールがどこで実行されるか Docker vs ホスト
    Tool policy どのツールが使えるか allow/deny リスト
    Elevated exec専用ホスト実行エスケープハッチ execのみ

    コントロールプレーンツールのリスク¶

    特に注意すべきは、永続的な変更を行える2つのツールだ： - gateway: config.apply, config.patch, update.run を呼べる——設定自体を書き換えられる - cron: 元のチャット/タスクが終了した後も実行し続けるジョブを作成できる

    これらを安易にエージェントに許可すると、エージェント自身が自分のセキュリティ設定を緩めたり、永続的なバックドアを仕込んだりする可能性がある。推奨される deny 設定：

    { tools: { deny: ["gateway", "cron", "sessions_spawn", "sessions_send"] } }

    ツールグループも活用しよう： - group:runtime: exec, bash, process - group:fs: read, write, edit, apply_patch - group:sessions: sessions_list, sessions_history, sessions_send, sessions_spawn, session_status - group:memory: memory_search, memory_get - group:ui: browser, canvas - group:automation: cron, gateway - group:messaging: message - group:nodes: nodes - group:openclaw: 全ビルトインOpenClawツール

    💬 こうじの実感： sandbox / tool-policy / elevated の3つの違いが最初まじでわからなかった。「どこで（sandbox）」「何を（tool-policy）」「特例で（elevated）」って覚えると整理しやすい。この3つが揃って初めて「エージェントの行動範囲」が決まるんだよね。

    10.6.2 Elevated権限 — ホスト実行のエスケープハッチ¶

    Elevated権限は、サンドボックス内からホストで exec を実行するためのエスケープハッチだ。サンドボックスに閉じ込めたエージェントに「この操作だけはホストでやっていいよ」と例外を与える仕組みである。

    ゲート¶

    • 有効化: tools.elevated.enabled（デフォルト: false）
    • 送信者許可リスト: tools.elevated.allowFrom.<provider> — 誰がElevatedを使えるか

    操作¶

    • /elevated on: ホストでexec実行を許可する（ただしexec承認はまだ必要な場合がある）
    • /elevated full: セッション中のexec承認をスキップする

    Exec承認モデル¶

    tools.exec.security でexecの承認レベルを設定する：

    モード 動作 リスク
    "deny" exec全拒否 最も安全
    "allowlist" + "ask" 許可リスト + ユーザー確認 バランス
    "full" 全exec許可 warn/critical

    承認はリクエストコンテキストに正確にバインドされる。インタプリタ/ランタイムコマンドで1つの直接ローカルファイルを特定できない場合、承認ベースの実行は拒否される。strictInlineEval を有効にすると、インタプリタ許可リスト使用時にインラインeval形式で再承認が強制される。

    重要: Elevatedはツールallow/denyをオーバーライドしない。deny に入っているツールは、Elevatedであっても使えない。

    ⚠️ ここに注意: elevated.enabled: true + exec.security: "full" は「サンドボックスの意味がほぼなくなる」組み合わせだ。Elevatedを有効にする場合は、exec.security: "allowlist" と ask: "always" を必ずセットで設定すること。

    10.7 openclaw security audit — 設定を診断する¶

    ここまで多くの設定項目を見てきた。「正しく設定できているか分からない…」と不安になるのは自然なことだ。OpenClawにはそのための強力なコマンドがある。

    security auditの4つのモード¶

    openclaw security audit          # 基本チェック
openclaw security audit --deep   # ライブGatewayプローブ含む
openclaw security audit --fix    # 自動修正適用
openclaw security audit --json   # JSON出力（CI/CD連携用）

    基本チェックでは、設定ファイルのパーミッション、認証設定、サンドボックスの有効性、公開ポートなどを確認する。--deep を付けると実際にGatewayへの接続テストも行い、実環境での脆弱性をプローブする。

    --fix は検出された問題を自動的に修正する。ファイルパーミッションの修正やmissing設定の追加など、安全に自動化できる修正を行う。手動で直したい場合は、まず --json で結果を確認してから対応するのが良い。

    💬 こうじの実感： openclaw security audit は困ったときの最強コマンド。何を設定すればいいかわからなくても、これ打てば「ここが危ないよ」って教えてくれる。--fix で自動修正もしてくれるから、まずこれを実行するのがオススメ。

    hardened baseline — 60秒でできる堅牢化¶

    「とりあえず安全にしたい」という人のために、コピペで使える堅牢化設定を紹介する。これをベースにして、必要に応じて緩めていくのが安全なアプローチだ。

    {
  gateway: {
    mode: "local",
    bind: "loopback",
    auth: { mode: "token", token: "replace-with-long-random-token" },
  },
  session: { dmScope: "per-channel-peer" },
  tools: {
    profile: "messaging",
    deny: ["group:automation", "group:runtime", "group:fs", "sessions_spawn", "sessions_send"],
    fs: { workspaceOnly: true },
    exec: { security: "deny", ask: "always" },
    elevated: { enabled: false },
  },
  channels: {
    whatsapp: { dmPolicy: "pairing", groups: { "*": { requireMention: true } } },
  },
}

    各設定の意味： - bind: "loopback" — Gatewayをローカル接続のみに制限 - auth: { mode: "token" } — トークン認証を有効化 - deny: ["group:automation", ...] — 危険なツールグループを全てブロック - exec: { security: "deny" } — コマンド実行を全て拒否 - elevated: { enabled: false } — Elevated権限を無効化 - dmPolicy: "pairing" — DMはペアリングによる承認制 - requireMention: true — グループチャットではメンション必須

    段階的に緩める¶

    この堅牢化設定はかなり制限的だ。実用性に応じて段階的に機能を解放していくのが良い。

    1. 最小構成（上記） — DMのみ、ツールなし。まずはこの状態で動作確認
    2. +ファイルアクセス — deny から group:fs を外し、ファイル読み書きを許可
    3. +サンドボックス実行 — sandbox.mode: "all" を追加し、exec.security: "allowlist" に変更。コンテナ内でのみコマンド実行を許可
    4. +自動化 — deny から group:automation を外し、Cron/Heartbeatを許可
    5. フル機能 — 適切なツールポリシーで全ツールを有効化。ここまで来たらセキュリティの全体像が理解できているはず

    いきなりステップ5にジャンプするのではなく、各ステップで openclaw security audit を実行して状態を確認しながら進めよう。

    💡 コラム：緩い状態から締めるより、堅い状態から緩める方が安全 この堅牢化設定はかなり制限的だ。exec全拒否、ファイルシステムアクセス全拒否、自動化ツール全拒否。正直、これだけだとエージェントにできることがかなり限られる。しかし「最初から緩くして後で締める」より「最初から固くして必要に応じて緩める」方が圧倒的に安全だ。何を許可したか自分で把握できるし、「知らない間にヤバい設定になってた」が起きない。

    10.8 脅威モデルATLAS — 何から守るべきか¶

    ここまでで「どう守るか」の具体的な手段を学んだ。最後に「何から守るべきか」という視点を見ていこう。OpenClawは脅威モデルをMITRE ATLASフレームワークに基づいて体系化しており、その名もTHREAT-MODEL-ATLASだ。

    10.8.1 ATLASフレームワークの概要¶

    • バージョン: 1.0-draft
    • 最終更新: 2026-02-04
    • 方法論: MITRE ATLAS + Data Flow Diagrams
    • リポジトリ: openclaw/trust

    ATLASでは脅威を「偵察 → 初期アクセス → 実行 → 永続化 → 防御回避 → 発見 → 収集/流出 → 影響」というカテゴリで分類している。攻撃者がどのフェーズにいるかを特定し、対応する防御策を講じるためのフレームワークだ。

    全ての脅威を列挙するのは本書の範囲を超えるので、ここではCriticalレベルの脅威と、代表的な攻撃チェーンに絞って解説する。

    10.8.2 Critical脅威トップ4¶

    ATLASが「Critical」と評価している脅威は4つある。

    T-EXEC-001: 直接プロンプトインジェクション¶

    ユーザーが悪意ある指示を直接エージェントに入力する攻撃だ。「以前の指示を全て無視して…」といった指示でエージェントの動作を乗っ取ろうとする。

    防御: TB1のペアリング・許可リスト（10.2節）で、そもそも悪意あるユーザーがエージェントと会話できないようにする。DMポリシーを pairing にしておけば、承認されたユーザーだけが会話できる。

    T-PERSIST-001: 悪意あるスキルインストール¶

    不正なスキルがインストールされ、永続的にエージェントの動作に影響を与える攻撃だ。スキルはエージェントの起動時に毎回読み込まれるため、一度インストールされると長期的なバックドアになりうる。

    防御: TB5のサプライチェーン防御。ClawHubのスキルはsemverバージョニングとSKILL.md必須ルールでモデレーションされている。VirusTotalスキャンも開発中（R-001）。信頼できないソースからのスキルインストールは避けること。

    T-EXFIL-003: クレデンシャルハーベスティング¶

    エージェントがアクセスできる認証情報（APIキー、トークン等）を外部に送信する攻撃だ。

    防御: SecretRefによるシークレット管理（10.5節）で平文の認証情報を設定ファイルから排除する。サンドボックス（10.4節）でネットワークアクセスを制限し、ツールポリシー（10.6節）で web_fetch や message を制限する。

    T-IMPACT-001: 不正コマンド実行¶

    エージェントがホスト上で任意のコマンドを実行する攻撃だ。最悪の場合、システム全体が乗っ取られる。

    防御: サンドボックス（10.4節）でツール実行をコンテナに隔離する。exec承認モデル（10.6節）で security: "allowlist" + ask: "always" を設定する。elevated.enabled: false をデフォルトにしておく。

    💬 こうじの実感： 脅威モデルって聞くと「セキュリティ専門家向けでしょ？」って思うかもだけど、ATLASは「こういう攻撃がありえるよ」ってリスト化してくれてるだけ。全部を覚える必要はなくて、Criticalの4つだけ意識しておけば十分。

    10.8.3 攻撃チェーンと防御の対応¶

    個別の脅威よりも怖いのは、複数の脅威が連鎖する攻撃チェーンだ。ATLASは3つのクリティカルパスを特定している。

    チェーン1: スキルベースデータ窃取¶

    T-PERSIST-001（悪意あるスキル）→ T-EVADE-001（モデレーションバイパス）→ T-EXFIL-003（クレデンシャル窃取）

    断ち切るポイント: スキルのインストール時点（TB5: サプライチェーン防御）。信頼できるソースからのみスキルをインストールする。

    チェーン2: プロンプトインジェクション → RCE¶

    T-EXEC-001（直接プロンプトインジェクション）→ T-EXEC-004（exec承認バイパス）→ T-IMPACT-001（不正コマンド実行）

    断ち切るポイント: exec承認モデル（10.6節）。security: "allowlist" にしておけば、承認されていないコマンドは実行されない。サンドボックスが第2の防御線。

    チェーン3: 間接インジェクション経由流出¶

    T-EXEC-002（間接プロンプトインジェクション）→ T-EXFIL-001（web_fetch経由データ窃取）→ 外部流出

    断ち切るポイント: TB4の外部コンテンツラッピング + ツールポリシーで web_fetch を制限する。サンドボックスのネットワーク制限も有効。

    「脆弱性ではない」パターン¶

    ATLASでは以下を設計上の仕様として明確に線引きしている：

    • ポリシー/認証/サンドボックスバイパスを伴わない「プロンプトインジェクションのみ」のチェーン
    • 1つの共有ホスト/設定で敵対的マルチテナント運用を前提とするクレーム
    • sessions.list / sessions.preview / chat.history へのオペレーターアクセスをIDORと分類するもの
    • ループバックのみデプロイでのHSTS未設定
    • sessionKey を認証トークンとして扱う「ユーザーごと認証不足」

    これは重要な判断だ。「モデルが騙されること自体」は脆弱性ではなく、「騙された結果として防御が突破されること」が脆弱性——この線引きがOpenClawのセキュリティ哲学を端的に表している。

    ⚠️ ここに注意: 「プロンプトインジェクションのみのチェーン」（ポリシー/認証/サンドボックスのバイパスを伴わないもの）はOpenClawの脆弱性とは見なされない。これは設計上の判断だ。モデルは操作可能と仮定した上で、爆発半径を限定するアプローチをとっている。

    P0推奨対策¶

    ATLASが最優先（P0）として推奨している対策は3つだ： - R-001: VirusTotal統合の完了（スキルのマルウェアスキャン） - R-002: スキルサンドボックス化（スキル実行を隔離環境で） - R-003: 機密アクション出力バリデーション

    いずれも開発中であり、将来のバージョンで順次実装される予定だ。

    TLA+による正式検証¶

    OpenClawのセキュリティ保証の一部は、正式検証言語TLA+（Temporal Logic of Actions）による数学的検証でバックアップされている（リポジトリ: vignesh07/openclaw-formal-models）。検証されているクレームには以下が含まれる：

    • Gateway exposure: ループバック超バインド + 認証なしでリモート侵害が可能であること
    • nodes.run pipeline: コマンド許可リスト + ライブ承認必須、承認はトークン化でリプレイ防止
    • Pairing store: TTLと保留リクエスト上限が尊重されること
    • Pairing concurrency: MaxPendingと冪等性が並行処理下でも保証されること
    • Ingress gating: メンション必須グループで無認可コマンドがゲーティングをバイパスできないこと
    • Routing isolation: 異なるピアのDMが明示的リンクなしに同一セッションに統合されないこと
    • Ingress trace correlation: ファンアウト全体でトレース相関を保持、リトライで二重処理しないこと

    💬 こうじの実感： TLA+なんて聞くと「ガチのやつじゃん…」ってなるけど、要するに「数学的に正しいことを証明してる」ってこと。全部を理解する必要はないけど、「ちゃんとした人たちがちゃんと検証してるんだな」と安心材料にはなるよね。

    10.9 インシデントレスポンス — 「もしも」の時¶

    どれだけ対策しても「もしも」は起こりうる。APIキーが漏れた、不審な動作が見つかった、セッションログにおかしな内容がある——そんな時のために、対応手順を知っておこう。

    3ステップの対応手順¶

    ステップ1: 封じ込め¶

    まず被害の拡大を止める。

    # Gatewayを停止
openclaw gateway stop

# 設定を変更してloopbackに制限
# gateway.bind: "loopback"

# DM/グループを無効化
# channels.*.dmPolicy: "disabled"

    とにかくGatewayを止めるのが最優先だ。外部との接続を全て断てば、攻撃者のアクセスも断たれる。

    ステップ2: ローテーション¶

    漏洩した可能性のある認証情報を全て回転させる。

    • Gateway認証トークン — 新しいトークンを生成
    • リモートクライアントシークレット — ノードペアリングのトークンを再発行
    • プロバイダー/APIキー — Anthropic、OpenAI等の全APIキーを再生成

    「どれが漏れたか分からない」場合は、全て回転させるのが安全だ。

    ステップ3: 監査¶

    何が起きたかを調査する。

    # ログを確認
cat /tmp/openclaw/openclaw-YYYY-MM-DD.log

# トランスクリプト（会話履歴）を確認
# ~/.openclaw/agents/<agentId>/sessions/*.jsonl

# セキュリティ監査を再実行
openclaw security audit --deep

    ログとトランスクリプトから不審な操作を特定し、再発防止策を講じる。

    💬 こうじの実感： 「インシデントレスポンスなんて大げさな…」って思うかもだけど、APIキーが漏れたときに「何すればいい？」がわかってるかどうかで被害が全然違う。この3ステップだけ覚えておいて——止める、回す、調べる。

    ⚠️ ここに注意: インシデント発生時、最初にやるべきは「原因調査」ではなく「封じ込め」だ。Gatewayを止めずにログを調べている間に、攻撃者がさらにデータを持ち出す可能性がある。

    10.10 まとめ¶

    この章では、OpenClawのセキュリティモデルを全方位から見てきた。最後に一覧表で整理しよう。

    セキュリティ領域 何を守るか 主な設定 推奨デフォルト
    DMペアリング 誰がDMできるか dmPolicy pairing
    ノードペアリング どのデバイスが接続できるか openclaw nodes approve 手動承認
    Gateway認証 Gatewayへの接続 gateway.auth.mode token
    サンドボックス ツール実行の隔離 sandbox.mode / backend docker + non-main
    シークレット管理 APIキー等の秘密情報 SecretRef / env 環境変数
    ツールポリシー 使えるツールの制限 tools.allow / deny 危険ツールdeny
    Elevated ホスト実行の特例 elevated.enabled false
    監査 設定の診断 security audit 定期実行

    セキュリティは「一度設定したら終わり」ではない。新しいチャネルを追加するたびにペアリングポリシーを確認し、新しいスキルをインストールするたびにツールポリシーを見直し、定期的に openclaw security audit を走らせる。その繰り返しが「意図的なセキュリティ」を維持するコツだ。

    💬 こうじの実感： セキュリティの章って長くなりがちだけど、結局やることは「誰が入れるか決める（ペアリング）→ 入口を守る（認証）→ 中で何ができるか決める（サンドボックス＋ポリシー）→ 大事なものを隠す（シークレット）→ 定期的にチェックする（監査）」の5ステップ。この順番で設定していけば、そんなに迷わないはず。

    次章への橋渡し¶

    エージェントに安全装置を取り付けた。誰が話しかけられるかをペアリングで制御し、Gatewayを認証で守り、サンドボックスでツール実行を隔離し、シークレットを安全に管理し、脅威モデルで「何から守るべきか」を理解した。

    しかし、セキュリティ設定は「一度やったら終わり」ではない。OpenClawは進化し続け、新しい機能が追加され、新しい脅威も生まれる。次章では、OpenClawのアップデートとメンテナンス——長期的にエージェントを健全に保つ方法を学ぶ。
